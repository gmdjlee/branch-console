## 1. 요지

**현행 레지스트리(0.1.0) 기준으로 w2026_structural은 서버·모바일 두 프로파일 모두 ORANGE에
도달하지 못한다** (최고 국면 AMBER, composite 최고치 35.15 — ORANGE 요건인 40에 미달).
D-14가 제안한 "2026-07-28을 세 번째 골든(양성, 극단 케이스)으로 승격"은 **이 리플레이
결과만으로는 시기상조**다 — 원인은 아래 §3의 vol_global 축 암전(부분은 데이터 결손, 부분은
실제 시장 거동)과, 그와 무관하게 composite 자체가 임계에 못 미치는 두 층위다. §4에 승격
시나리오 초안 두 가지를 제시한다.

## 2. 두 프로파일 리플레이 결과

| 지표 | server_intraday | mobile_daily |

두 프로파일의 composite 최고치가 정확히 일치하는 것은 우연이 아니다 — 최고치가 발생한

"같은 근거로 같은 산출"을 낸다는 점에서 이는 오류가 아니라 정합성의 증거다.

### 2.2 앵커일(2026-07-28) 상태 — "리드타임"이 성립하지 않음

D-14 문서와 `backtest/windows.yaml`의 `anchor_hint: 2026-07-28`(참고 최대낙폭일)에서:

| | server_intraday (kr_close, 17:00) | mobile_daily (확정 틱, 16:20) |
|---|---|---|
| phase | **GREEN** | **AMBER** |
| composite | 22.70 | 22.70 |
| coverage | 0.758 | 0.758 |
| distinct_axes | 2 | 2 |
| fired_axes | `kr_flow_price`, `rates_fx` | `kr_flow_price`, `rates_fx` |
| any_crit | true | true |

ORANGE에 전혀 도달하지 못했으므로 "첫 ORANGE 대비 앵커일 리드타임"이라는 지표 자체가
정의되지 않는다(분자가 없음) — BACKTEST_PLAN §6 리드타임 판정표의 "2026-07 창은 07-28
이전 도달" 기준은 이 창에서 **미충족**이다.

server가 GREEN인데 mobile이 AMBER인 차이의 원인을 최초 승격 sustain 히스테리시스
"가능성"으로 서술했으나 **오서술이었다** — 실측 확인한 실제 기전은 다음과 같다
(MT0-04 aaa-critic 라운드1 F-4 정정):

`usdkrw_z(3.0)+vkospi_z(2.5)+kospi_drawdown(2.5) = 8.0/31.0`은 cadence
`intraday_30m`이고 server의 intraday_30m 스테일 창은 90분이다(`configs/indicators.yaml
engine.stale_profiles.server_intraday.intraday_30m` — 이 값 자체가 BACKTEST_PLAN §BT-03
스윕 대상 ④ "스테일 창"이며, 아래 수치는 이 가설값 하에서의 관측이지 결함이 아니다).
일봉 근사에서 이 세 지표는 T 당일 kr_close(17:00 KST) 틱에서만 그날치 값이 가시화되고,
그 다음 server 틱(다음 날 us_close, +14.5시간)이면 이미 90분을 넘겨 stale이 된다 — 즉
**하루 16개 server 틱 중 kr_close 단 1틱에서만 살아있다.**

실측(2026-07-27~29, kr_flow_price/rates_fx 발화가 이 세 지표에 의존하는 구간):

| 시각 | composite |
|---|---|
| 07-28 15:30 | 0.0 |
| 07-28 17:00 (kr_close) | 22.695 (≥20, AMBER 조건 충족) |
| 07-29 07:30 | 0.0 |

AMBER 조건(`composite_gte: 20` 또는 `or_any_crit`)을 충족하는 틱이 이렇게 앞뒤로
0.0에 둘러싸인 **고립된 단일 틱**이면, `promote_sustain_ticks=2`(연속 2틱 요구)는
구조적으로 도달 불가능하다 — kr_close 틱만으로 얻는 근거로는 server가 영구히 승격되지
못한다(다른 축이 우연히 인접 틱에서도 동시에 조건을 채우는 날에만 예외적으로 승격되며,
이 창에서 관측된 server 20회 전이 중 일부가 그런 경우다). 반면 mobile_daily는 하루
1틱뿐이고 그 1틱이 바로 이 kr_close 상당 시점(확정 틱)이라 "고립"이라는 문제 자체가
없고, `promote_sustain_ticks=1`이라 그 틱 하나로 즉시 승격된다.

정확히 하기 위해 부연: 위 "하루 내내 0.0"은 intraday_30m 3종에 한정된 현상이지 그
날의 다른 지표 전부가 0.0이라는 뜻이 아니다. `daily_us`(36h)·`daily_kr`(36h)·
`fred_daily`(72h) cadence 지표들은 스테일 창이 하루(24h)보다 길어 하루 안에서는 절대
깨지지 않으므로, 그 지표들의 severity는 그날 16개 server 틱 내내 **동일값으로 고정**
된다. 하루 안에서 composite가 변하는 유일한 원인은 intraday_30m 3종(가중 8.0/31.0)이
kr_close 직후에만 반짝 살아있다가 90분 뒤 사라지는 것뿐이다.

### 2.3 composite 포화 여부

최고치 35.15는 ORANGE 임계(40)에 4.85점 부족하고, RED 임계(60)에는 크게 못 미친다.
distinct_axes는 이 창에서 최대 3(server 848틱 중 6틱만, mobile 53틱 중 6틱)까지만
관측됐고 — ORANGE의 `distinct_axes_gte: 2`는 여러 날 충족됐지만(mobile: distinct_axes>=2인
틱 21/53) `composite_gte: 40`이 항상 병목이었다. **포화는 없다** — F-06(해상도) 논의의
전제인 "severity 3 동시 고정"이 발생할 정도로 지표들이 강하게 발화하는 국면 자체가 이
근사-PIT 데이터셋에서는 나타나지 않았다.

## 3. vol_global 축 암전 — 원인 두 층위

`vol_global`(가중 7.0 = vix_level_z 3.0 + vix_term_structure 2.5 + move_index_z 1.5)은
**이 창 전체(2026-05-15~07-31 평가구간) 동안 두 프로파일 어디서도 단 한 번도 발화(severity
>= warn)하지 않았다.**

### 3.1 층위 A — 데이터 결손(가중 4.0/7.0): ^MOVE·^VIX3M 2026-07-17 야후 절단

`backtest/fixtures/w2026_structural.meta.json`(BT-01)과 이번 리플레이 스테일 판정이 함께
확인: ^MOVE·^VIX3M 두 계열은 2026-07-17 이후 야후(K-01/K-18, 비공식 API) 관측이 완전히
끊겼다(BT-01 REPORT §4: `^MOVE 2026-07-20~2026-07-31 10세션 공백`, `^VIX3M` 동일). 이
리플레이는 이를 특수 케이스로 흡수하지 않고 `engine_ref.registry.is_stale`
(`configs/indicators.yaml engine.stale_profiles`)로 자연 처리한다 — 07-17의 마지막 관측이
가시화된 시점부터 시간이 흐르며, mobile daily_us 스테일 창(48h) 초과 시점(07-23 확정 틱,
가시화 후 사흘째)부터 `vix_term_structure`(2.5)·`move_index_z`(1.5) 두 지표가 구조적으로
결측 처리된다(server는 daily_us 36h 창이라 더 일찍, 07-22쯤부터). 이 시점부터 앵커일
07-28까지 vol_global 가중 7.0 중 **4.0이 공백** — **앵커일(07-28)은 이 공백의 내부에
있다.** mobile coverage가 절단 이전 0.887(전 지표 가시)에서 07-23 이후 0.758로
떨어지는 시점이 정확히 이와 일치한다(4.0/31.0 ≈ 0.129 = 0.887−0.758; §2.1 표의
"최저 coverage 0.548"은 **이 절단과 무관한 별도 사건**이다 — 실측 확인 결과 06-22
확정 틱에서 us_market 기반 지표 5종(vix_level_z·vix_term_structure·move_index_z·
dxy_z·spx_drawdown_momentum, 가중 10.5)이 함께 결측이며, 06-19(미국 Juneteenth
휴장 추정)발 야후 공백이 mobile daily_us 스테일 창(48h)을 넘긴 결과로 보인다 —
같은 "us_market 그룹 일괄 결측" 패턴이지만 원인 사건(6월 미국 휴장 vs 7월 야후
비공식 API 절단)과 결측 지표 조합이 다르므로 §3.1의 논의와 직접 연결 짓지 않는다).

### 3.2 층위 B — 남은 vix_level_z(3.0)도 이 창 평가구간 내내 watch 미만

층위 A만이 원인이라면 "^MOVE·^VIX3M 결손이 없었다면 vol_global이 발화했을 것"이라는
추정이 성립해야 한다. 그러나 확인 결과 **그렇지 않다**: 결손의 영향을 받지 않는
`vix_level_z`(^VIX, 가중 3.0)는 평가구간(2026-05-15~07-31) 전체에서 최고 z-score가
1.2314278746875487(watch 임계 1.5 미달)에 그쳤고, `vix_term_structure`도 절단 이전
구간에서 최고 0.9857928748726832(watch 임계 0.95는 근소 초과, warn 1.00 미달)이었다
— 즉 **데이터가 살아있던 구간에서도 vol_global의 두 살아있는 지표는 watch를 겨우
넘거나 못 넘는 수준에 머물렀다.**

**출처 정정(MT0-04 aaa-critic 라운드1 F-3)**: 위 두 수치는 `backtest/results/
metrics.json`에서 직접 읽을 수 있는 값이 **아니다** — 그 파일은 지표별 z-score가
아니라 창×프로파일별 (composite, coverage, distinct_axes, fired_axes) 틱 레코드만
담는다(브리프 산출물 범위, `run_replay.py`의 `replay_window_profile` 참조). 위
수치는 `engine_ref`로 그 자리에서 재계산한 것이며, 아래 스니펫으로 그대로
재현된다(저장소 루트에서 실행):

```python
import pandas as pd
import backtest.run_replay as rr
from engine_ref import registry

window = {w.window_id: w for w in rr.load_windows()}["w2026_structural"]
df = pd.read_parquet("backtest/fixtures/w2026_structural.parquet")
grid = rr.trading_days(df, window)  # 평가구간 거래일 그리드
specs = {s.id: s for s in registry.load_indicator_specs(enabled_only=True)}
ctx = rr._Ctx(df, grid, {}, {}, "mobile_daily", rr.time(16, 20))

for ind_id, builder in [
    ("vix_level_z", rr._build_vix_level_z),
    ("vix_term_structure", rr._build_vix_term_structure),
]:
    runtime = builder(specs[ind_id], ctx)
    known = runtime["known"]
    # 평가구간(그리드 범위)으로 제한 -- padding 구간 값은 어떤 틱에서도 조회되지 않는다.
    in_range = [
        (d, v)
        for d, v in zip(known.row_dates, known.values, strict=True)
        if grid[0] <= d <= grid[-1]
    ]
    best_date, best_val = max(in_range, key=lambda x: x[1])
    print(f"{ind_id}: max={best_val!r} on {best_date}")
# 출력: vix_level_z: max=1.2314278746875487 on 2026-06-10
#       vix_term_structure: max=0.9857928748726832 on 2026-06-05
```

`build_indicator_runtime`이 아니라 `_build_vix_level_z`/`_build_vix_term_structure`를
직접 부르는 이유는 두 지표의 값을 개별 조회하기 위함이며, 실제 리플레이(`replay_window_
profile`)는 동일 함수를 15개 지표 전부에 대해 내부적으로 호출한다 — 재현 경로가
운영 경로와 다르지 않다.

**해석**: "국내 구조 증폭형 대폭락"(D-14의 성격 규정)이라는 이름 그대로, 이 사건은 글로벌
변동성 지수가 크게 반응하지 않은 채(혹은 반응했어도 야후 결손으로 못 본 채) 국내
축(`kr_flow_price`·`rates_fx`)이 주로 발화한 사건으로 근사-PIT 데이터가 재구성된다. D-01의
"역사적 분기점은 예외 없이 2개 축 이상 동시 발화"라는 전제가 이 창에서는
`kr_flow_price`+`rates_fx`(간헐적 `global_price`)로 채워지고 `vol_global`은 관측되지
않는다 — vol_global 결손분(4.0/7.0)이 데이터 문제이고 나머지(3.0)는 실제 시장 거동일
가능성이 있다는 이 이중 구조는 C1 실측 이전에는 완전히 분리해 확정할 수 없다(층위 A 없이
vix_level_z가 최종적으로 얼마나 올랐을지는 알 수 없다 — 다른 계열이 살아있었다는 사실이
vix_level_z 자체가 극값을 쳤을지의 증거는 아니다).

## 4. 승격 시 D-08 개정안 초안 (사용자 승인 대기, D-14 규율)

D-14: "승격은 사용자 승인 후 D-08을 개정하는 방식으로만 한다." 아래 두 안을 제시한다 —
**본 서브태스크(MT0-04)는 어느 안도 채택하지 않는다.**

### 안 ⓐ (권고): 승격 보류, BT-03 이후 재평가

§3의 두 층위 중 층위 A(데이터 결손)는 C1(실측 lake, 야후 대안·Stooq 폴백 등)에서만 완전히
해소된다. 층위 B(실제 vol_global 미발화)가 진짜 시장 거동이라면, 그 자체는 F-04(KR 구조
지표 2종: `krx_halt_events`·`margin_leverage_stress`, 현재 `enabled: false`)가 채우려는
정확히 그 공백이다 — BT-03에서 F-04 활성 시나리오를 이 창에 재실행해보지 않고 D-08을
개정하면, "글로벌 축이 조용해도 감지된다"는 골든의 취지 자체가 이 창에서 충족되는지 알 수
없는 채로 동결하게 된다. **BT-03(F-04 활성 검토 포함) 완료 후 재리플레이해 재평가할 것을
권고한다.**

### 안 ⓑ (참고, 비권고): 현재 관측치를 그대로 동결

부득이 지금 승격한다면, 현재 관측된 산출을 있는 그대로 D-08에 추가하는 형태만 정직하다
(원하는 결과를 얻기 위해 임계·가중치를 조정하는 것은 BACKTEST_PLAN §BT-02 완료 기준과
`docs/AAA_QUALITY_STANDARD.md` 규율 위반 — "보정은 BT-03의 몫"):

```yaml
# D-08 개정안(안 ⓑ, 비권고) — 세 번째 골든(양성): w2026_structural
# 주의: 레지스트리 0.1.0 기준 ORANGE 미도달 — "극단 케이스"라는 D-14의 성격 규정과
# 실제 도달 국면(AMBER)이 불일치한다. 채택 시 D-14의 "극단 케이스" 서술도 함께 수정 필요.
third_golden:
  window_id: w2026_structural
```
