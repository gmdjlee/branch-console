# MT1-00b — ECOS item_code 실측 확정: 차단(ECOS_API_KEY 부재)

- 작성: 2026-08-07, data-verifier Worker
- 대상: `configs/indicators.yaml`의 `krx_credit_spread_delta.source.item_codes`
  (`corp_aa3y: VERIFY`, `ktb_3y: VERIFY`, K-04) 실측 확정 — **미완료, 차단 상태로 보고**

## 0. 결론 (요지)

실호출을 시도하기 전 사전 점검(브리프 지시 1단계) 단계에서 **`ECOS_API_KEY`가 `.env`에
존재하지 않음**을 확인했다. `configs/sources.yaml:33`이 명시하는 `auth: env:ECOS_API_KEY` 없이는
ECOS StatisticItemList/StatisticSearch API를 인증 호출할 수 없다(공개 무인증 엔드포인트가 없음 —
ECOS는 모든 조회에 발급 키를 요구). 브리프 1단계 지시("키명은 .env에서 직접 확인. 없으면 중단하고
보고")에 따라 **API 실호출을 0회 수행**하고 여기서 중단한다.

`configs/indicators.yaml`의 VERIFY 2건은 **변경하지 않았다**(추측 코드 금지 원칙). K-02(VKOSPI)처럼
사전 정의된 fallback 경로가 K-04에는 없으므로 fallback도 활성화하지 않았다 — 이 항목은 그대로
"미해결" 상태로 남겨 사실을 문서로 대체한다.

## 1. 사전 점검 절차 및 실측 사실

**절차**: `.env` 파일의 변수명만 나열(값은 미출력) — `grep -oE "^[A-Z_]+=" .env`.

**실제 결과**:
```
ANTHROPIC_API_KEY=
FRED_API_KEY=
KRX_ID=
KRX_PW=
```
4개 키만 존재. `ECOS_API_KEY`는 파일에도, OS 환경변수(`printenv | grep -i ECOS`, 결과 없음)에도
없다.

**대조 확인**: `configs/sources.yaml:29-35`
```yaml
ecos:
  kind: rest
  base: "https://ecos.bok.or.kr/api"
  auth: env:ECOS_API_KEY
  stats:
    - { stat_code: "721Y001", note: "시장금리(일별) — item_code는 구현 시 API 응답으로 검증 (함정 K-04)" }
```
설정이 요구하는 환경변수명(`ECOS_API_KEY`)과 `.env`의 부재가 정확히 일치 — 오타·별칭 문제가
아니라 키 자체가 발급/등록되지 않은 상태다.

## 2. 시도하지 않은 것 (범위 외로 남김, 추측 방지)

- ECOS `StatisticItemList`(메타 조회) 호출: **미시도** — 인증키 없이는 401/오류만 반환할 것이
자명하여 실호출 자체가 무의미(브리프의 "실호출 최소화" 원칙과도 부합).
- ECOS `StatisticSearch`(데이터 검증 조회) 호출: **미시도**, 동일 이유.
- 웹 검색·공개 문서로 "국고채 3년/회사채 AA-3년 항목코드가 보통 이렇다"는 추정: **하지 않음** —
  브리프가 "추측으로 코드값을 채우지 마라"고 명시했고, ECOS `721Y001` 하위 item_code는 공개
  문서만으로 확정할 수 없는(계층형 코드가 버전마다 바뀔 수 있는) 값이라 실측 없이 기록하면
  위험하다.

## 3. 확정 반영

- `configs/indicators.yaml` — **무변경**(`VERIFY` 2건 그대로 유지).
- `configs/sources.yaml` — **무변경**.
- git 커밋 없음(변경 사항이 없어 커밋할 대상이 없음 — 브리프의 커밋 문구
  `m1-00b: verify ECOS item codes...`는 이번 세션에서 사용하지 않는다. 실제로 코드값을 확정한
  뒤에만 그 메시지가 정확하다).

## 4. 재개 조건 (Advisor·사용자 판단 필요)

1. ECOS(한국은행 경제통계시스템, ecos.bok.or.kr) Open API 페이지에서 **API 인증키를 신규 발급**
   (무료, 이메일 인증 — 계정 신청 자체는 이 Worker 권한 밖).
2. 발급받은 키를 `.env`에 `ECOS_API_KEY=<키>` 형식으로 추가(다른 3개 키와 동일 파일, 코드/yaml에
   노출 금지 — CLAUDE.md K-17류 원칙과 동일 적용).
3. 위 두 조건이 갖춰진 뒤 본 브리프(MT1-00b)를 그대로 재실행하면 2단계(메타 조회 1~2회 +
   검증 조회 2회)부터 정상 진행 가능하다. 이번 세션에서 확인한 사전 점검·환경 사실(§1)은

## 7. 재개(2026-08-08, 사용자가 ECOS_API_KEY 발급·`.env` 등록) — 실호출 4건, **critical 발견으로 재차단**

`.env`에 `ECOS_API_KEY=` 존재 확인(값 미열람·미기록). 브리프 2단계 지시대로 최소 실호출
(메타 1~2회+검증 2회 예산 내에서 메타 2회+검증 2회 = 총 4회)로 진행했다. **결론부터: item_code
자체는 확정했으나, SSOT의 `stat_code: "721Y001"`이 애초에 일별 데이터를 제공하지 않는 잘못된
통계표코드임을 실측으로 확인했다** — 이는 브리프가 가정한 전제(721Y001이 일별 테이블)를 뒤집는
사실이라 §3에서 "무변경"으로 남긴 `configs/indicators.yaml`을 이번 재개에서도 **여전히 수정하지
않는다**(사유는 §7.4).

### 7.1 메타 조회 1 — `StatisticItemList/.../721Y001` (SSOT가 지정한 통계표코드)

`GET https://ecos.bok.or.kr/api/StatisticItemList/{key}/json/kr/1/200/721Y001` 1회 호출 —
`list_total_count=90`, 90건 **전량 수신**(누락 없음, 페이지네이션 불필요).

**실측 결과**: 90건의 `CYCLE` 분포는 `{A: 30, M: 30, Q: 30}` — **`D`(일별) 사이클이 단 1건도 없다**.
응답의 `STAT_NAME` 필드 원문: `"1.3.2.2. ○○금리(연,분기,월)"`(연·분기·월 전용 표기가 통계표 이름
자체에 박혀 있음). 즉 `configs/sources.yaml:35`·`indicators.yaml:75`의 "시장금리(일별)" 주석은
**실측과 다르다** — 721Y001은 연/분기/월 데이터만 제공하며, `krx_credit_spread_delta`가 요구하는
`cadence: daily_kr`·`delta_bp(..., lookback=5)`(5거래일 변화) 계산에 애초에 쓸 수 없다.

### 7.2 메타 조회 2 — `StatisticItemList/.../817Y002` (일별 시장금리 후보, 실측으로 확정)

721Y001이 일별이 아니므로, ECOS 통계 체계상 형제 관계로 보이는 "1.3.2.1" 코드를 실측 조회했다
(추측 아님 — 721Y001 응답의 `STAT_NAME`이 스스로 "1.3.2.2"라 밝혀, 직전 번호 "1.3.2.1"이 일별
짝일 가능성을 API 응답이 시사했고, 이를 실제 호출로 검증한 것).

`GET https://ecos.bok.or.kr/api/StatisticItemList/{key}/json/kr/1/200/817Y002` 1회 호출 —
`list_total_count=27`, 27건 전량 수신. `STAT_NAME="1.3.2.1. 시장금리(일별)"`, **전 항목
`CYCLE=D`**. 필요한 두 계열을 실측 확인:

| ITEM_CODE | ITEM_NAME(원문) | CYCLE | START_TIME | END_TIME | DATA_CNT | UNIT_NAME |
|---|---|---|---|---|---|---|
| `010200000` | 국고채(3년) | D | 19981113 | 20260807 | 6873 | 연% |
| `010300000` | 회사채(3년, AA-) | D | 19950103 | 20260807 | 8023 | 연% |

(참고, 채택하지 않음: `010310000` "회사채(3년, AA-, 민평)"는 2002-08-19부터 시작하는 **다른
계열**(민간채권평가사 평균치 방법론) — indicators.yaml 지표명 "회사채(AA-,3y)"와 명칭이 완전히
일치하는 쪽은 `010300000`이라 이것을 채택했다. 항목명에 "민평" 수식어가 붙지 않은 표준 계열.)

임계(watch 6/warn 10/crit 20bp, **5일 변화폭** 기준)는 이 절대 수준이 아니라 변화량에 걸리므로
정합적이다(예: 07-20→07-27 변화 +1.6bp는 watch 미만, 정상 범위).

**지연 특성(T+1 확인)**: 조회 종료일을 `20260808`(호출 시점의 "오늘")로 열어뒀음에도 **최신 행은
`20260807`(전영업일)에서 끊긴다** — 오늘자 값은 아직 발행되지 않음. `indicators.yaml:78`의
`lag_days: 1`은 이 실측과 **일치**(수정 불필요).

**결측/휴장 표기 방식(FRED와 다름, MT1-04d 반영 필수)**: FRED는 결측일에 `"value": "."`처럼
자리값을 채운 행을 준다(00a 저널 §12 참조 계열과 달리 ECOS는 실측 결과 **행 자체가 생략**된다 —
주말 4일(07-25·26, 08-01·02)에 대응하는 행이 응답에 전혀 없다(list_total_count=15가 2026-07-20
~2026-08-07 사이 영업일 수와 정확히 일치, 캘린더일수 19일에서 주말 4일을 제외). 즉 "null 값이
있는 레코드"가 아니라 "그 날짜의 레코드 자체가 없음" — 소비자는 날짜 존재 여부로 결측을 판정해야
하며, 값 필드의 null 체크만으로는 결측을 못 잡는다.

**필드 타입(원문 확인)**: `DATA_VALUE`는 **JSON 문자열**(`"3.895"`, 숫자 아님 — 파싱 시 `float()`
변환 필수), `TIME`은 `"YYYYMMDD"` 8자리 문자열.

### 7.4 [critical, 재차단] stat_code 자체가 SSOT에 잘못 기재됨 — item_codes만 교체 시 설정이 깨짐

**확정 사실**: `configs/indicators.yaml:74`의 `stat_code: "721Y001"`은 일별 데이터를 전혀 제공하지
않는(§7.1, CYCLE 전량 A/M/Q) 통계표다. `krx_credit_spread_delta`가 실제로 필요로 하는 국고채(3년)·
회사채(3년,AA-) 일별 금리는 **`stat_code: "817Y002"`** 아래 `item_code 010200000`·`010300000`에
있다(§7.2, §7.3로 실측 확정). 이 둘은 서로 다른 통계표이며 item_code 네임스페이스도 겹치지 않는다
(721Y001의 90개 item_code는 `1010000`·`5020000`·`7020000`류 — 817Y002의 `010200000`류와 전혀
다른 체계, §1의 원 메타 조회 결과 참조).

**이번 브리프의 지시("VERIFY 2건을 실측 코드로 교체... 다른 키 수정 금지")를 문자 그대로 따르면**
`item_codes: { corp_aa3y: "010300000", ktb_3y: "010200000" }`로 바꾸되 `stat_code: "721Y001"`은
그대로 두게 되는데, **이 조합은 실행 시 반드시 빈 응답/오류를 낸다**(721Y001에는 그 item_code가
존재하지 않음, §7.1). VERIFY 표식이 사라져 "해결됨"처럼 보이지만 실제로는 조용히 깨진 설정을
심게 되는 셈이라, 이대로 반영하지 않았다.

**Worker 권한 판단**: `stat_code` 교정은 이번 브리프·재개 지시 양쪽이 명시한 "다른 키 수정 금지"
범위를 벗어난다(이번에 지시받은 것은 `item_codes` 2건뿐). 두 필드가 원자적으로 결합된 값이라
하나만 고치면 더 나쁜 결과(조용한 실패)가 되므로, **`configs/indicators.yaml`을 이번에도 무변경으로
남기고 여기서 멈춘다** — 추측 없이 확정한 사실만 보고하고, 실제 반영 여부·범위 확장 승인은
Advisor·사용자 판단으로 남긴다(MT0-03 §1·§3 선례와 동일한 처리: 권한 밖 수정은 재현 절차와
근거만 제공).

**권고(승인 시 반영할 diff, 참고용 — 미반영)**:
```yaml
source:
  provider: ecos
  stat_code: "817Y002"          # 시장금리(일별) — 2026-08-08 실측: 721Y001은 CYCLE A/M/Q뿐, 일별은 817Y002 (§7.1-7.2)
  item_codes: { corp_aa3y: "010300000", ktb_3y: "010200000" }   # 2026-08-08 실측 확정(§7.2-7.3, StatisticSearch 값 확인)
  cadence: daily_kr
  lag_days: 1                    # 실측 T+1 확인, 변경 불필요 (§7.3)
```

### 7.5 MT1-04d 구현 계약 (참고용 초안, 이 문서 안에만 기록 — §7.4 승인 후 유효)

**요청 규격**:
- 메타(선택, 최초 1회/캐시): `GET https://ecos.bok.or.kr/api/StatisticItemList/{authkey}/json/kr/1/200/817Y002`
- 데이터: `GET https://ecos.bok.or.kr/api/StatisticSearch/{authkey}/json/kr/1/{n}/817Y002/D/{start:YYYYMMDD}/{end:YYYYMMDD}/{item_code}` —
  인증키가 URL 경로 세그먼트에 그대로 들어간다(헤더 아님) → 로그·크래시리포트에 요청 URL 전체가
  찍히지 않도록 주의(K-17류, 기존 `FredCredentialsProvider` 패턴처럼 키를 EncryptedSharedPreferences로
  보관하고 요청 직전에만 URL을 조립).
- 응답 파싱: 최상위 키 `StatisticSearch.row[]`, 각 행 `{TIME(문자열 YYYYMMDD), DATA_VALUE(문자열,
  float 변환 필요), UNIT_NAME}`. `corp_aa3y`·`ktb_3y` 두 계열은 item_code가 다르므로 **호출 2회**
  필요(1회 호출에 항목 4개까지 묶을 수 있는 API 규격이 있으나 이번 실측에서 시도하지 않음 — 구현
  단계에서 별도 확인).

**결측 처리(§7.3 확정 사실)**:
- 해당 날짜의 행이 **없으면 결측**(FRED처럼 값 `"."` 채운 행이 오지 않음) — `expected trading day
  set`(KRX 캘린더)과 응답 `TIME` 집합의 차집합으로 결측일을 도출해야 한다. 단순히 "row가 왔으니
  ok"로 판정하면 안 되고, 요청한 날짜 범위 대비 실제로 온 날짜 수를 대조해야 한다.
- `DATA_VALUE`가 빈 문자열이거나 파싱 불가한 경우는 이번 실측(15건 전부 정상 숫자)에서 관측되지
  않았다 — 방어적으로 `float()` 실패 시 결측 처리하는 코드는 필요하지만, 실제 발생 사례로 확정된
  것은 아니다(추측과 방어적 코딩을 구분해 기록).
- 방어적 오류 분기(이번 세션에서 실제 오류 응답은 재현하지 못함, 확정 사실 아님 — 구현 시 별도
  확인 권장): ECOS는 결과가 없거나 인증 실패 시 `row` 없이 `RESULT.CODE`/`RESULT.MESSAGE` 봉투만
  반환하는 것으로 알려져 있다 — 최상위에 `row` 키 부재 시 오류/무데이터로 분기하는 방어 코드를
  권장하되, 이는 이번 4회 호출로 직접 재현한 사실이 아님을 명확히 한다.

**as-of/PIT(K-05류)**: §7.3에서 T+1을 실측 확인했다(`lag_days: 1` 그대로 유효). `observed_at`
(수집 시각, KST)과 `as_of`(데이터 기준일=TIME 필드)를 분리 기록하고, PIT 조인은 `as_of` 기준으로
한다는 기존 lake 규약(sources.yaml 공통 규칙)을 그대로 따르면 된다 — 이번 실측으로 새로운 예외를
발견하지 않았다.

**폴백**: 지정된 fallback 없음(K-04 정의 범위 밖). §7.4가 미해결인 상태에서는 MT1-04d 착수 자체가
차단 유지가 맞다(PROGRESS.md "MT1-04d 블록 유지" 기존 기재와 일치).
