## D-15. 시스템 분리 — 역할 정의 (확정)

두 시스템은 **동일한 SSOT(configs/·contracts/·prompts/)를 공유하는 독립 실행체**다. 어느 한쪽이 죽어도 다른 쪽은 완결적으로 동작한다.

| | **모바일 `branch-console-android`** | **서버 `branch-console` (Python)** |
|---|---|---|
| 사명 | 일 단위 국면 분석 + 사용자 요청 시 최신 갱신(프리뷰) | 24/7 분기점 감시(장중 30분 틱), 놓치지 않는 것 |
| 실행 주체 | 주력폰(Android), WorkManager 일일 작업 + 수동 갱신 | 미니PC 8745HS(D-09), systemd/Docker 상주(APScheduler) |
| 틱 | **확정 틱 1회/일**(KR 마감 후 16:20 KST) + 프리뷰(수시, 비확정) | 30분 틱(장중), 기존 설계 그대로 |
| 수집 | 네이티브 REST 직접 호출(CORS 없음): FRED·ECOS·KRX(kotlin_krx)·야후계·KIS(옵션) | 기존 collectors(yfinance/fred/pykrx/ecos/scrape) |
| 원장 | Room(SQLite) append-only + 일 1회 Drive 백업 | Parquet PIT lake + Postgres |
| 판단 | Claude API 직결(구조화 출력), 티어링 동일 | 동일 |
| 알림 | 로컬 노티 + 홈 위젯 | 텔레그램 + Grafana |
| 뉴스 축 | v1 비활성(enabled:false 유지) | P2(S2)에서 활성 |
| 백테스트 | 골든 리플레이 계측 테스트(패리티) | DuckDB 실측 PIT(C1) |

경계 규칙: 모바일은 서버의 존재를 가정하지 않는다(INT 이전). 서버는 모바일의 존재를 가정하지 않는다.
연동은 INT 단계에서 "서버가 발행한 스냅샷을 모바일이 **추가 소스**로 소비"하는 단방향으로만 붙는다(§D-21).

## D-16. 상태기계 프로파일 이원화 (확정)

기존 히스테리시스 파라미터(승격 sustain 2틱, 강등 6틱, dwell 4틱)는 **30분 틱을 전제**로 보정된 값이다.
일 단위 틱에 그대로 쓰면 승격에 2일, 강등에 6일이 걸려 시스템 목적(적시 경보)과 충돌한다. 따라서
`configs/statemachine.yaml`에 `profiles:` 블록을 신설하고 엔진은 프로파일 파라미터를 주입받는다.
**전이 구조·composite 공식(D-02)·distinct_axes 요건·skip_levels는 프로파일과 무관하게 동일**하다 — 달라지는 것은 틱 단위 카운트뿐이다.

```yaml
# statemachine.yaml 추가 (CHANGES_V3 §2에 전체 패치)
profiles:
  server_intraday:           # 기존 값 그대로 이관 (의미 변화 없음)
    tick: 30m
    promote_sustain_ticks: 2
    demote_below_ticks: 6
    min_dwell_ticks: 4
  mobile_daily:              # 신규 — 전부 가설, BT-03 보정 대상 (D-04 규율 적용)
    tick: 1d
    promote_sustain_ticks: 1   # 일봉 확정치 기준 즉시 승격 (2026-07 갭하락형 대응)
    demote_below_ticks: 3
    min_dwell_ticks: 2
```

골든 케이스(D-08)는 **두 프로파일 모두** 통과해야 한다. mobile_daily용 골든 기대값(일봉 리샘플 타임라인)은
BT-02에서 확정해 `backtest/golden_mobile.yaml`로 기록한다. 이후 전 phase의 공통 회귀 게이트는
"골든 × 2프로파일 무회귀"로 확장된다.

## D-17. 프리뷰(온디맨드 갱신) 비확정 규율 (확정)

수동 갱신은 **지금 시점의 잠정 composite·지표 심각도를 계산해 표시만** 한다.

1. 프리뷰는 국면 전이를 **커밋하지 않는다**. 국면 확정은 일일 확정 틱에서만 일어난다. (장중 플래핑·히스테리시스 오염 차단 — 서버 30분 틱의 sustain 규율을 일 1틱 시스템에서 대체하는 장치)
2. 프리뷰 결과가 crit 레벨을 넘으면 "잠정 경보" 로컬 노티는 허용하되, UI에 항상 `PREVIEW` 배지와 데이터 시각(as_of)을 표기한다.
3. 프리뷰 수집치도 Room lake에 append한다(observed_at=now). 일일 확정 틱은 마감 기준 as-of로 읽는다 — PIT 규율(D-06) 유지.
4. 프리뷰는 LLM을 **자동 호출하지 않는다**(비용 가드). 시나리오 리포트 생성은 명시적 버튼으로만.

## D-18. SSOT 공유 방식 — 단일 저장소, 자동 동기화, 패리티 게이트 (확정)

```
branch-console/                  # 단일 저장소 (모노레포)
├── configs/  contracts/  prompts/     # SSOT — 유일한 진실, 양 시스템 공용
├── engine_ref/                        # [M0 신설] 순수 Python 참조 엔진 (백테스트·서버 공용)
├── backtest/                          # [M0 신설] 하니스·픽스처·골든 기대값
├── mobile/                            # [M1 신설] Android 프로젝트 (Kotlin·Compose)
├── collectors/ lake/ detection/ ...   # 서버(기존 구조 유지, S1에서 engine_ref 재사용)
└── docs/  .claude/
```

- **configs → 모바일**: Gradle task `syncConfigs`가 루트 `configs/*.yaml`·`prompts/*.md`를 `mobile/app/src/main/assets/`로 복사하고, 계측 테스트가 SHA-256 해시 일치를 검증한다(수동 복사·드리프트 금지, 함정 K-16).
- **contracts → 모바일**: pydantic 모델을 kotlinx.serialization 데이터클래스로 미러하고, **스키마 스냅샷 파일을 공유**해 Python/Kotlin 양쪽 테스트가 같은 스냅샷과 대조한다. 파괴적 변경은 기존 규칙대로 `/2` 승격.
- **엔진 패리티**: `engine_ref`(Python)가 계산 명세의 실행 가능한 정의다. Kotlin 엔진은 동일 픽스처 입력에 대해 |Δcomposite| ≤ 0.05, 국면 타임라인 완전 일치를 만족해야 한다(BT-05, GM1 게이트 조건).

## D-19. 개발 순서 역전과 백테스트 하니스 신설 (확정)

모바일 우선 개발의 전제 조건은 "임계·프로파일이 검증된 레지스트리를 assets로 굽는 것"이다. 그런데 실측 PIT 보정(C1)은
서버 lake가 있어야 가능하다. 이 순환을 끊기 위해 **M0에서 Python 백테스트 하니스를 개발기 계기(instrument)로 신설**한다:

- Claude Code 안에서 실행되는 개발 도구다(배포물 아님). yfinance/FRED/pykrx 소급 수집으로 근사-PIT 픽스처를 만들고, engine_ref로 9창(양성 7·음성 2)을 리플레이한다.
- 산출: 레지스트리 0.3.0(D-12 양방향 임계 1차 보정, F-04 활성 판정, mobile_daily 프로파일 보정, F-06 해상도 대응안) → 모바일 v1에 반영.
- 한계를 명시한다: 소급 수집 데이터는 개정치(revision) 반영본일 수 있어 진짜 PIT가 아니다. 따라서 **최종 확정은 여전히 C1(서버, 실측 lake)** 이며, BT 결과는 "1차 보정 + 정합성 계측"으로 지위를 한정한다. (2026-08-01 아티팩트 백테스트의 "근사치" 한계를 체계적으로 승계·해소하는 단계)

### 20.3 재검증 절차 (유지)

ID는 고정하되 **분기 C-주기마다 모델 목록을 실조회**해 신규 세대·폐기 일정(deprecation)을 확인하고,

## D-22. 기능 동등성 매트릭스 — 모바일 v1은 "서버 − 상시가동"이 아니다 (확정)

### 22.3 결론과 규율

모바일 v1은 **"감지·판단 파이프라인은 완전 동등, 판단의 재료(analogue·뉴스·HMM)는 축소"** 다.
따라서 온보딩·앱 정보 화면의 v1 한계 고지(MT2-06)에 "장중 감시 없음" 뿐 아니라 **G-1~G-3을 함께 적는다** —
사용자가 리포트의 진폭 추정을 서버판과 동일한 신뢰도로 읽으면 안 되기 때문이다.
INT(D-21) 완료 시 G-1~G-3은 서버 스냅샷 소비로 해소되며, 그 시점에 고지 문구를 갱신한다.

## D-23. 온디맨드 분석의 결과 동등성 — 커버리지·결측 규율 (확정)

검증 질문: "사용자가 모바일에서 분석을 지시하면 서버와 같은 결과가 나오는가."
**답: 아니다. 그리고 무보정 상태에서는 방향까지 어긋날 수 있다.** 원인은 3층위로 분리된다.

### 23.1 층위 A — 설계상 의도된 차이 (버그 아님)

프리뷰는 국면을 커밋하지 않는다(D-17). 서버의 매 틱 산출물은 *확정 국면*이지만
모바일 수동 분석의 산출물은 *잠정 지표값 + 잠정 composite*다. **출력물의 종류 자체가 다르다.**
또한 히스테리시스는 틱 단위 카운트이므로 프로파일이 다르면(D-16) 같은 데이터라도 국면 타임라인이 갈린다.

### 23.2 층위 B — 결정론 영역: 엔진은 같고 **입력이 다르다**

BT-05 패리티가 보장하는 것은 "동일 입력 → 동일 산출(\|Δcomposite\|≤0.05)"뿐이다. 입력이 갈리는 지점:

| 원인 | 내용 |
|---|---|
| as-of 차이 | 서버 장중 틱은 실시간값, 모바일 확정 틱은 종가 기준 |
| 제공자 신선도 | 야후계 지연, FRED T+1, ECOS·KRX 일 단위 |
| **장중 결측** | KRX계 4지표(가중 8.5)는 장중 조회 불가(KIS 미사용 시). CDS 1.5는 모바일 경로 없음(G-4) |

**결측이 만드는 왜곡이 핵심 위험이다.** `missing_data_policy: exclude_from_denominator`(D-02) 때문에
결측 지표는 분모에서 빠진다. 장중 프리뷰에서 유효 가중이 21.0/31.0(67.7%)로 줄고 남은 지표가 전부 글로벌이면:

- 글로벌 지표가 일제히 severity 2, 국내 지표는 (조회됐다면) 0인 상황
- 모바일 프리뷰: 100×(21.0×2)/(21.0×3) = **66.7** + 발화 축 4개 → **RED 조건 충족**
- 서버 동시각: 100×(21.0×2 + 10.0×0)/(31.0×3) = **45.2** → **ORANGE**

즉 **국내가 잠잠하다는 사실이 점수에서 사라져 프리뷰가 국면을 한 단계 과대평가**한다.
반대로 국내만 급변하고 글로벌이 조용한 국면에서는 과소평가가 발생한다. 방향성 오류이므로 반드시 처리한다.

### 23.3 규율 (프리뷰 전용, 확정 틱에는 적용 금지)

1. **Carry-forward**: 프리뷰는 결측 지표에 대해 **직전 확정값을 이월**해 분모를 유지하고, 해당 지표 카드에 `as_of`와 스테일 배지를 표시한다. 이월값은 Room에 새 레코드로 쓰지 않는다(원장 오염 금지).
2. **커버리지 표기**: 유효 가중 / 전체 가중 비율(coverage %)을 프리뷰 화면 상단에 항상 표시한다.
3. **판정 억제**: coverage < 80%면 composite 수치를 흐리게 처리하고 "국면 판정 불가"로 표기한다. 잠정 경보도 발신하지 않는다.
4. **확정 틱은 예외 없음**: carry-forward 금지, 결측은 D-02대로 분모에서 제외, `stale_profiles`(D-16) 초과 값은 무효 처리. PIT 규율이 우선한다.
5. **리포트 버튼은 확정 스냅샷에서만 활성**한다. 프리뷰 상태(이월·스테일 혼재)로 LLM 리포트를 만들면 근거가 흔들린다.

### 23.4 층위 C — 본질적으로 재현 불가

동일 evidence-pack이라도 LLM 서술·`subjective_prob`는 매 호출 달라진다(서버끼리도 동일하지 않다).
**재현 가능한 것은** `trigger` 블록·composite·`fired_indicators`·품질 게이트 PASS/FAIL 판정뿐이다.
여기에 D-22의 G-1~G-3(analogue·뉴스·HMM 부재)이 더해져 **evidence 자체가 다르므로**, 리포트 본문의 동등성은 v1에서 성립하지 않는다.

### 23.5 무엇을 보장하는가 (동등성의 정확한 정의)

"동일 결과"가 아니라 **"동일 규칙 + 설명 가능한 차이"** 를 보장 대상으로 삼는다:

| 보장 | 수단 |
|---|---|
| 동일 SSOT(임계·가중·프롬프트·티어링) | syncConfigs + SHA-256 계측 테스트 |
| 동일 입력 → 동일 산출 | BT-05 패리티 |
| 동일 출력 스키마 | contracts 스냅샷 공유 |
| 차이의 설명 가능성 | 커버리지 표기 + 프로파일 명시 + as_of 표기 |
| 확정 국면의 실측 일치율 | **INT 게이트 신규 조건**: 병행 운영 30일간 동일 일자 확정 국면 일치율 ≥ 90%, 불일치는 전부 프로파일·틱 차이로 설명 가능해야 함 |

## D-21. 서버↔모바일 연동(INT) 범위 사전 정의 (범위만 확정, TASK는 S3 게이트 후 작성)

- 방향: 서버 → 모바일 단방향. 서버가 매 틱 `scenario-snapshot/1`·상태 요약 JSON을 발행(1안: Drive 파일 동기화 — P4 모듈 C 계승 / 2안: Tailscale 내 read-only HTTP).
- 모바일은 "서버 소스"를 **추가 provider**로 등록: 있으면 서버 데이터 우선 표시(30분 신선도 확보), 없거나 stale이면 자체 수집으로 폴백. 자체 일일 확정 틱은 계속 돈다(이중화).
- P4 모듈 C(앱 연동 API)는 INT로 흡수·폐지. 모듈 A/B는 선택 확장으로 존치.
