# AAA_QUALITY_STANDARD — 품질 표준·비평 프로토콜·다중 에이전트 절차

- 작성일: 2026-08-02 · 적용: 전 트랙·전 phase · 판정 주체: `aaa-critic` 서브에이전트(수정 권한 없음, 판정 전담)
- 원칙: "AAA"는 수사가 아니라 **측정 가능한 관문**이다. 아래 기준을 통과하지 못한 항목은 완료로 표기할 수 없다.

---

## 1. 판정 체계

- 단위: TASK의 서브태스크(MT-xx/ST-xx/BT-xx) 및 phase 게이트.
- 등급: **PASS**(전 기준 충족) / **CONDITIONAL**(경미 결함 ≤ 2건, 24h 내 해소 조건부 — 게이트에는 사용 불가) / **FAIL**(반려 사유 목록 필수).
- 루프: 구현 → `qa-verifier`(기계 검증: 테스트·SSOT 스캔) → `aaa-critic`(본 루브릭 판정) → FAIL이면 반려 사유를 브리프에 첨부해 재위임. **수렴할 때까지 반복**한다. 동일 항목 3회 연속 FAIL이면 Advisor가 구조 문제(설계 결함·기준 모순)로 재분류해 사용자에게 보고한다 — 무한 루프 방지와 "완벽 추구"의 균형점.
- 비평가 자세: 실제 상용 시스템 담당자가 인수 검사한다고 가정한다. 애매하면 FAIL. 칭찬 서술 금지, 결함 목록과 재현 절차만.

## 2. 루브릭 (도메인별 하드 기준)

### 2.1 로직 (정확성)
- [ ] 골든 무회귀 × 2프로파일, 음성 창 오탐 0 (BACKTEST_PLAN §6)
- [ ] PIT 규율: as-of 정렬 테스트, look-ahead 차단 테스트(K-11), append-only 강제(DAO/모듈 수준) 증명
- [ ] 수치: float64/Double 고정(K-07), 경계값(임계 등호)·결측(분모 제외)·타임존(KST/UTC 명시, naive 금지 K-05) 단위 테스트
- [ ] Kotlin↔Python 패리티(해당 시): |Δcomposite| ≤ 0.05, 국면 타임라인 일치

### 2.2 기능 (완결성)
- [ ] TASK 완료 기준·요구 시나리오 체크리스트 100% + 명세 밖 동작 없음
- [ ] 실패 경로 전부 정의된 UX: 네트워크 단절 / 부분 결측(지표별 stale 배지) / API 키 미설정·오류 / 쿼터 초과 / 프로세스 중단 후 캐치업 — "빈 화면·무한 스피너·조용한 실패" 금지
- [ ] 멱등성: 같은 날짜 확정 틱 재실행이 상태를 오염시키지 않음

### 2.3 유지보수성
- [ ] 린트 0 경고: Python `ruff` / Kotlin `ktlint`+`detekt` (기본 룰셋, 억제 주석은 사유 필수)
- [ ] 테스트: 코어 모듈(engine·statemachine·contracts·lake) 라인 커버리지 ≥ 90%, 나머지 ≥ 70%; 전 테스트 네트워크 금지·픽스처 기반
- [ ] SSOT 위반 0: 임계·가중치·프롬프트·모델 ID 하드코딩 스캔 통과, configs/contracts/prompts 무단 수정 없음
- [ ] 의존성 버전 핀(uv.lock / gradle version catalog), 문서 동시 갱신(변경이 문서 가정을 깨면 같은 커밋에서 문서 수정)

### 2.4 디자인·그래픽 (모바일 UI, M2~)
- [ ] 디자인 토큰 단일 소스(`mobile/.../ui/theme/Tokens.kt` — 색·타이포·간격·모서리·모션 전부 토큰 경유, 리터럴 금지). 규격은 `.claude/skills/design-system` 준수
- [ ] 국면 컬러 시스템: GREEN/AMBER/ORANGE/RED가 색+형태(아이콘·라벨) 이중 부호화 — 색약 사용자 구분 가능
- [ ] 다크/라이트 완전 대응, 대비 WCAG AA(본문 4.5:1), 터치 타깃 ≥ 48dp, 글꼴 스케일 1.3× 무파손, TalkBack 주요 화면 라벨
- [ ] 모션: 국면 전이·새로고침·차트 등장 애니메이션 정의(120~300ms, 토큰화), 과장 금지
- [ ] 성능 예산: 콜드 스타트 < 2s(중급기), 홈 스크롤 정크 프레임 < 1%(macrobenchmark 계측), 위젯 갱신 < 1s
- [ ] 완성 요소: 앱 아이콘(적응형)·스플래시·빈 상태 일러스트·오류 상태 그래픽까지 제작(placeholder 금지)

### 2.5 상용 대비 체감 검사 (M2·M3 게이트 전용)
비평가는 상용 증권·핀테크 앱의 홈 대시보드(예: 토스증권·KIS MTS류)를 기준 심상으로 두고 다음을 점검한다:
첫 화면 3초 내 "현재 국면·근거 상위 3지표·데이터 시각" 파악 가능 / 숫자 타이포(탭ular figures) 정렬 / 로딩 스켈레톤 /
당겨서 새로고침 관성 / 어색한 여백·잘린 텍스트·기본 Material 티 나는 화면 0곳. 하나라도 "상용이면 반려될 수준"이면 FAIL.

## 3. Plan Council — 다중 에이전트 계획 절차 (phase 착수 전 필수)

1. Advisor가 phase 목표·제약·입력 문서를 담은 공통 브리프 작성.
2. `plan-architect` **2~3 인스턴스를 한 메시지로 병렬 위임**, 각자 배타적 관점을 전담하되 **각자 완전한 전체 계획**을 작성한다: ① 아키텍처·의존성 ② 데이터·정합성·백테스트 ③ UX·운영·실패경로.
3. `aaa-critic`가 각 계획을 루브릭 §2 + 상호 모순 검사로 판정. FAIL 계획은 반려 사유와 함께 해당 인스턴스에 재작성 위임. **전원 PASS까지 라운드 반복**(라운드마다 비평 기록을 docs/reviews/에 남긴다).
4. Advisor가 수렴본을 비교·병합해 TASK 문서 확정(차이가 남으면 결정 근거를 D-xx로 기록).
5. 사용자 승인 → 착수.

## 4. 실행 강도 (ultracode / effort / ultrathink)

- **세션**: 매 세션 시작 프롬프트에 ultracode 활성을 지시한다(세션 한정 설정 — xhigh 추론 + 동적 워크플로 오케스트레이션). 대량 병렬 시 토큰 소모가 크므로 단순 유지보수 세션은 기본 effort로.
- **턴**: 설계 결정·비평 판정·회귀 원인 분석 턴에는 프롬프트에 `ultrathink` 키워드. 기계적 작업(리네임·포맷)에는 쓰지 않는다.
- **모델 배정**: Advisor(메인 세션) = `claude-opus-5`. plan-architect·aaa-critic = `claude-opus-5`(`effort: xhigh`),
  구현·검증 Worker = `claude-sonnet-5`. 전체 ID로 고정하고 `CLAUDE_CODE_SUBAGENT_MODEL`은 설정하지 않는다(D-20 §20.2).
  품질 판정을 하위 모델로 내리는 것은 금지 — 게이트가 게이트 구실을 못 한다.
- **주의**: 워크플로 내 서브에이전트는 편집 자동 승인으로 동작할 수 있다. SSOT 디렉토리 보호는 에이전트 규칙 + (선택) PreToolUse 훅으로 이중화한다(CLAUDE.md §7).

## 5. 기록

비평 판정은 `docs/reviews/`에 phase별 로그로 누적한다(판정·반려 사유·해소 커밋). 게이트 리포트는 이 로그를 인용해야 한다.
